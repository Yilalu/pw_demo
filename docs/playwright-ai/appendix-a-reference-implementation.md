# Appendix A — Reference Implementation (Example Only)

> This appendix shows how the generic guidance maps onto **one real repository**, a small demo web app used to prove out the workflow. Copy the **patterns**, not the specifics. Your app, folders, fixtures, and rules will differ.

## 1. How the example is wired

```text
.github/agents/
  playwright-test-planner.agent.md     ← generated by init-agents --loop=vscode, plus a "project context" block
  playwright-test-generator.agent.md
  playwright-test-healer.agent.md
.github/workflows/
  playwright.yml                       ← CI: npm ci → install --with-deps → test → upload report
  copilot-setup-steps.yml              ← prepares the machine used by the GitHub Copilot coding agent
.vscode/mcp.json                       ← registers the "playwright-test" server (run-test-mcp-server)
docs/prompt/{planner,generator,healer}.md  ← reusable prompts
specs/                                 ← plans (Planner output)
tests/
  seed.spec.js                         ← seed: signs in a synthetic user via fixture
  e2e/<suite>/<scenario>.spec.js       ← Generator output
  fixtures/index.js                    ← extends test with testUser + authenticatedPage
  pages/*.js                           ← page objects
  utils/test-users.js                  ← synthetic account factory (UUID-based emails)
playwright.config.js                   ← baseURL, webServer (starts the app), chromium project
```

How the app starts doesn't matter to the tooling. In this example, `webServer` in `playwright.config.js` starts it, so neither the agents nor developers start it by hand.

## 2. Patterns worth copying

### 2.1 Synthetic-user fixture (no real credentials anywhere)

```js
// tests/fixtures/index.js (pattern)
export const test = base.extend({
  testUser: async ({ request }, use) => {
    const user = createTestUser();                       // unique email per test
    const res = await request.post('/api/auth/register', { data: user });
    expect(res.status(), `account setup failed: ${await res.text()}`).toBe(201);
    await use(user);
  },
  authenticatedPage: async ({ page, testUser }, use) => {
    await new LoginPage(page).goto();
    await new LoginPage(page).login(testUser.email, testUser.password);
    await page.waitForURL('**/dashboard');
    await use(page);
  },
});
```

Why it matters for AI: the agent rules can say "use `testUser` / `authenticatedPage`", so the Generator never makes up credentials or duplicates login steps.

### 2.2 Project-context block in each agent file

The generator's block encodes:
- language: plain JS `.spec.js`, no TypeScript syntax
- path: `tests/e2e/<suite-kebab>/<scenario-kebab>.spec.js`
- imports from the fixtures module, with the relative path computed
- reuse page objects; one test per file; titles match the plan
- synthetic data only; don't import the seed; no assertions on volatile external data
- ask when the plan is unclear; don't run the suite unless asked

The planner's block encodes **route coverage**: every route must have at least one scenario, plus a coverage matrix. The healer's block encodes **edit scope** (the failing test only; never app code or config).

### 2.3 Seed that exercises the real auth path

The seed signs in through the UI with a fixture-provisioned user, so the Planner and Generator start from the same state real tests see.

## 3. Issues found in the reference project

These are real instances of the drift pitfalls in [08 §5](./08-troubleshooting-and-known-issues.md#5-instructions-and-settings-that-contradict-each-other). They show what to look for in your own repo.

| # | Where | What was wrong | What it caused | How to fix it |
| --- | --- | --- | --- | --- |
| 1 | Planner and Healer agent files | They say Playwright only looks for tests in `tests/e2e/`, but the config's `testDir` is `./tests`, the whole folder | `npx playwright test --list` shows the seed test as a normal test, so it also runs in CI | Either change `testDir` to `./tests/e2e` and run the seed separately, or correct the sentence in the agent files |
| 2 | Saved Generator prompt (`docs/prompt/generator.md`) | It asks for TypeScript files (`.spec.ts`) in `tests/<suite>/`, while the Generator agent file requires JavaScript (`.spec.js`) in `tests/e2e/<suite>/` | Depending on which instruction the AI follows, tests end up in the wrong language or folder | Make the prompt match the agent file |
| 3 | Saved Planner/Healer prompts and project docs | They mention files and folders that don't exist (`tests/example.spec.js`, `examples/`, `postman/`) | The AI wastes time looking for them, and readers get confused | Remove the mentions, or add the files |
| 4 | Copilot setup workflow (`copilot-setup-steps.yml`) | The build step says `npx run build` instead of `npm run build` | The Copilot coding agent's machine fails during setup | Correct the command |
| 5 | Agent files | They say the app is started with one command, but the config's `webServer` actually starts two separate commands (server and client) | When startup fails, the AI suggests the wrong fix | Describe what `webServer` really does |
| 6 | Healer agent file vs saved Healer prompt | The agent file allows `test.fixme()` (skip a test when the app is broken). The prompt forbids it. | The Healer behaves differently depending on which instruction wins | Decide on one rule and write it in both |
| 7 | `.vscode/mcp.json` | Uses `npx.cmd`, which exists only on Windows | The agents' server can't start for Mac and Linux teammates | Use `npx` in the shared file |
| 8 | `.env.example` | Contains a sample email and password | People or the AI might use them as real login details, against the fake-data rule | Remove them. The test fixtures create users automatically. |
| 9 | Planner agent's tool list | Includes `browser_run_code_unsafe`, which can run any code on the computer | Unnecessary risk, since the Planner doesn't need it to write plans | Remove it from the Planner's tool list |

## 4. Example prompts used with this project

**Planner**
```text
Create a test plan for the site at <baseURL>. Call planner_setup_page once first.
Cover every route with at least one independent scenario and include a route-coverage matrix.
Plan registration and login separately; login provisions its own account.
Synthetic data only. Do not plan purchases or assert values from external services.
Save to specs/<app>-test-plan.md with Seed: tests/seed.spec.js. Do not write tests.
```

**Generator**
```text
Generate one test.
- Plan: specs/<app>-test-plan.md  - Suite: <exact>  - Scenario: <exact>
- File: tests/e2e/<suite-kebab>/<scenario-kebab>.spec.js  - Seed: tests/seed.spec.js
- Steps/expected: <verbatim>
```

**Healer**
```text
Fix the failing test.
- File: tests/e2e/<suite>/<scenario>.spec.js  - Title: <exact>
- Failure output: <paste>
```
